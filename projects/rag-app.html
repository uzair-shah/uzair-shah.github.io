Ask-a-PDF Question Answering (RAG) with Model Comparison

A small app that answers questions about a research paper using only the paper's text, then tests how accurately and quickly two AI models do it.

Python · Sentence-Transformers (all-MiniLM-L6-v2) · ChromaDB · Gemini (gemini-3-flash-preview) · DeepSeek-R1 via Ollama · FastAPI · Docker

View the code on GitHub

What it does

  • Answers plain-English questions about one PDF: Gregory Warrington's 2005 maths paper 'Juggling Probabilities' (American Mathematical Monthly).
  • Uses retrieval-augmented generation (RAG): it first finds the most relevant passages, then asks an AI model to answer using only those passages.
  • The model is told to say so honestly when the paper doesn't contain the answer, rather than making something up.
  • Compares a cloud model (Google Gemini) against a model running locally on a laptop (DeepSeek-R1 via Ollama) on accuracy and response time.
  • Also exposes the pipeline as a web API: POST a question to /ask/ and get an answer back (FastAPI).

The data

  • Input is a single PDF stored in the repo: Warrington-JugglingProbabilities-2005.pdf.
  • Text is extracted page by page, then cleaned with regular expressions to strip licence lines, journal headers, null characters and blank lines.
  • The cleaned text is cut into 800-character chunks that overlap by 100 characters so ideas aren't split mid-thought.
  • The saved vector database (chroma_db/) holds 50 embedded chunks in a collection named 'juggling_paper'.

How it works

  1. 1
    Read the PDFpypdf · pdf_to_text()

    Extracts text from every page of the juggling paper into one string.

  2. 2
    Clean the textre · clean_text()

    Removes licence boilerplate, journal headers, null characters and empty lines.

  3. 3
    Chunkchunk_text(text, 800, 100)

    Splits text into 800-character pieces overlapping by 100 characters (50 chunks stored).

  4. 4
    Embed & storeall-MiniLM-L6-v2 · ChromaDB (./chroma_db)

    Turns each chunk into a vector and saves it locally; skipped if the collection already has data.

  5. 5
    Retrievesearch()

    Embeds the question and fetches the closest chunks (top 3 in evaluation, top 5 in the API).

  6. 6
    Answerask_llm_gemini() / ask_llm_deep_seek()

    Sends the passages plus the question to an LLM told to answer only from the context.

    If GeminiCloud call to gemini-3-flash-preview with a pause and up to 3 retries; otherwise DeepSeek-R1 runs locally via Ollama.
  7. 7
    Scorescore_query() · run_eval()

    Checks each answer for expected keywords (or refusal phrases for trick questions) and records response time.

How it's evaluated

A hand-written test set of 12 questions (test_queries.txt) checks both correct answers and correct refusals.

10 answerable questionsAcross categories: easy facts (author, year), metadata (references, page count), definitions, a theorem explanation, a synthesis comparison, a vague 'main idea' question and a specific historical fact.
2 trick questions'Banana sandwich recipe' and 'Did the egg come before the chicken?' — the model passes only if it refuses (e.g. says the context 'does not' contain it).
Keyword scoringAn answerable question passes if the reply contains at least one expected keyword (e.g. 'Warrington' or 'Gregory' for the author).
TimingEach model call is timed; for Gemini, a deliberate 20-second rate-limit pause is subtracted from the measured time.

Results

Saved notebook output from one run of all 12 test questions (top 3 retrieved passages per question):

Gemini: 10 / 12 passedMissed 'What are the references' and 'What's the main idea?'. Correctly refused both trick questions.
DeepSeek-R1: 9 / 12 passedMissed the same two questions, and failed to refuse 'Banana sandwich recipe'.
Gemini: 4.76 s average responseRanged from 2.57 s to 8.22 s per question.
DeepSeek-R1: 31.37 s average responseRanged from 15.54 s to 59.92 s per question, about 6.6× slower than Gemini on a local laptop.

The author's own takeaways: local models work end-to-end on a laptop; quality drops depend on question type; reasoning models like DeepSeek-R1 trade a lot of latency for thinking and aren't always right for RAG; Gemini Flash performed better than DeepSeek-R1 8B.

Inside the code

RetrievalQuestion and chunks are embedded with all-MiniLM-L6-v2; ChromaDB returns the nearest chunks by distance score.
Embed onceEmbeddings are only computed when the ChromaDB collection is empty, so reruns skip re-encoding.
Grounded promptRetrieved chunks are joined under a 'Context:' header followed by the 'Question:', with a system instruction to use only that context.
Retry with backoffGemini calls retry up to 3 times with exponential backoff on API errors.

Limitations (noted by the author)

  • Keyword scoring isn't fully reliable: DeepSeek said an answer wasn't in the context but answered anyway, and the test didn't catch it.
  • DeepSeek-R1 may need more parameters to perform better.
